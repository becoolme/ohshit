Apify 表示，未经授权的第三方进入了部分内部系统，并使用失陷的凭据取得部分账户凭据，随后访问相关账户。截至 11 月 12 日，Apify 已通知个人信息或存储数据遭访问的客户。各账户涉及哪些数据，以发给该客户的通知为准。早期公开通报未披露受影响客户数量和完整数据范围；下文初步报告补充了类别，但没有公布总数。

Apify 已切断访问路径、加强监控、轮换关键内部密钥，并出于预防考虑吊销部分第三方 OAuth 连接。Apify 表示，调查暂未发现攻击者通过这些连接进入系统。使用 GitHub 私有仓库构建的 Actor 可能需要重新授权。早期通报称，确认用户令牌受影响后会轮换并通知；初步报告现已确认轮换，完整根因及已完成处置的报告仍待发布。

11 月 13 日，Apify 表示调查仍在进行，并已改为只存储 API 令牌的哈希值。Apify 建议所有客户限制存储访问，因为当资源开放时，任何知道存储 ID 的人都可以读取其中的数据。这是一项预防措施；Apify 并未认定开放存储是本次入侵所用的路径。通过 Apify 官方支持核实事件通知，不要提供密码、双重验证代码或付款信息。

11 月 16 日，Apify 称已修复最可能的初始入口，并在 11–13 日加固攻击路径各环节。公司扩大了哈希与加密的覆盖、进一步限制高权限访问并轮换更多内部凭据。调查仍在进行，尚未发现新的未授权访问。


**11 月 20 日初步报告：** 攻击者最初持有可用的 Apify API 令牌，其中包括一枚高权限员工令牌，随后利用网络服务中此前未知的漏洞进入内部会话缓存。被盗会话包括高权限员工会话，令攻击者可通过内部管理工具批量读取账户记录。少量活跃账户的部分存储数据也遭读取。报告未说明最初如何取得可用令牌，未指明攻击者、受影响账户总数，也未分配 CVE。

报告区分网络路径与凭据复用：工程师报告的一项无关漏洞修复收紧了网络规则，于 11 月 10 日 18:00 UTC 关闭内部路径，当时团队尚未识别入侵。已被盗凭据仍可使用，直至 11 月 11–12 日轮换。状态页记载发现时间为 11 月 11 日 12:13 UTC，初步报告将事件响应开始记为 12:00 UTC，来源未解释这 13 分钟差异。早期状态更新称自 11 月 11 日以来未发现攻击者继续活动，较新报告则称自 11 月 12 日以来未检测到活动。两种表述均不能证明此前访问没有危害。

对于完整记录被读取的账户，报告确认密码的加盐 bcrypt 哈希、2FA 密钥及恢复码遭读取。若账户存有付款卡，读取的记录包含持卡人姓名、到期日及末四位；Apify 称从不存储完整卡号或账户明文密码。平台称加密的秘密 Actor 输入字段及秘密环境变量未暴露。这些排除项不抵消其他账户记录、会话、API 令牌和少量账户存储数据已遭访问的事实。

Apify 称已结束全部控制台会话、轮换受影响 API 令牌及代理密码、吊销 GitHub 连接并轮换集成 OAuth 凭据。现仅保存 API 令牌与会话密钥的哈希，并对代理密码、2FA 密钥及恢复码使用哈希或加密。缓存中包含 GitHub 连接令牌；11 月 11 日 14:20 UTC 吊销时也移除了部署密钥。厂商尚未发现其被使用的迹象，仍建议检查 GitHub 安全日志。完整认证记录遭读取的账户所有者应按通知重置密码及 2FA；客户须自行在工作流中替换已轮换凭据。11 月 20 日状态条目标记已解决，同时明确调查仍在继续，之后还会发布完整报告。
