GitBook 初始通知将基础设施凭据访问置于 11 月 2 日 19:00 CET（18:00 UTC）；下述完整复盘修订了这一概略时间。公司将定向攻击归于 AI 智能体，但未指明框架或攻击者。下述较新复盘补充攻击路径及三条 IP，尚未公布 CVE 或受影响客户数量。确认的平台访问支持 L4；所列客户资料类别仍属可能被访问，并非已确认每个组织都受影响。

11 月 3 日 16:21 CET 公告取代 13:15 CET 时“暂不需操作”的立场：轮换现有 GitBook 及关联第三方凭据、已发布集成密钥，并重新认证 MCP。GitBook 称已阻断攻击者、关闭漏洞并更换基础设施凭据。公司未发现客户内容被修改的证据，但这不能排除读取或后续发现。11 月 3 日称应用、API 及文档恢复可用但部分降级；该状态现由下述恢复公告更新。尚无证据证明与 WorkOS／ARTEX 或其他近期事件有关。

**下游文档应对：** PancakeSwap 11 月 3 日原帖称，已将文档从 GitBook 迁到自管基础设施并恢复，保留既有链接。此前原帖明确称其文档未遭入侵、应用未受影响，下线为预防措施。这不能确立交易所入侵、钱包窃取脚本植入或客户损失，也不取代 GitBook 的凭据轮换要求。

**11 月 4 日恢复：** 11:36 CET（10:36 UTC），GitBook 宣布事件解决、平台功能恢复；Git Sync 仍受另一起 GitHub 故障影响。上述令牌、密钥轮换及 MCP 重新认证要求仍有效，公司承诺 24 小时内发布完整复盘。可用性恢复不能独立证明所有客户均已完成操作，也未确定可能遭访问资料的最终范围。

**11 月 4 日完整复盘（20:30 CET／19:30 UTC）：** GitBook 称 SSO 登录流程缺陷允许伪造员工会话，再查询配置错误的内部 GitHub App 认证信息，进入代码仓库并取得 Cloudflare API key，继而通过生产秘密和服务账户获取基础设施访问。公司将全部客户资料按暴露处理，而非只处理定向目标，但这不等于已确认所有资料被读取。可访问内容包括 API、集成及会话签名秘密、需认证的文档和 docs／spaces／change requests；GitHub／GitLab 访问限于客户授予集成的仓库，是否有实际仓库操作无法确定。公司称账单资料、密码及 IP 地址未遭泄露，未发现客户内容被修改的证据。

复盘 UTC 明细修订早期概略时间：11 月 2 日 12:27 首个目标客户账户遭劫持，16:32 取得员工会话及代码，17:48 进入生产，18:10 告警，19:58 修补 SSO，20:32 禁用账户并下线。11 月 3 日 02:34 开始重新部署并吊销既有 API 令牌，03:09 部署新 Cloudflare Workers，06:00 准备新凭据发布，10:52 轮换 GitHub App 密钥，11:56 全部秘密轮换并恢复在线，22:51 轮换 GitLab 同步令牌。另报告 11 月 2 日约 2 小时 45 分钟及 11 月 3 日约 40 分钟的生产访问窗口，但未给出后一窗口完整起止；不能将下线时间当作最终清除的唯一证据。较早概略时间保留为历史描述。

应完成新增的自定义认证密钥更新及仓库排查；GitBook 代管同步密钥已轮换，不代表客户自有第三方凭据已轮换。原文客户操作列表称 Git Sync／GitLab 无需操作，影响表另写必要时重连，两种表述均保留并建议向支持核实。此前 MCP 重新认证及 Assistant 提问风险评估仍有效。公司归因于自动化／AI 的描述不构成特定框架或共同攻击者的独立证据。
